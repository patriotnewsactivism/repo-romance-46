# Security Policy

RepoFinisher handles source-code access, repository write authority, AI provider credentials, and user-owned analysis data. Security failures can therefore affect both RepoFinisher and repositories it is authorized to modify.

## Reporting a vulnerability

Do not post active credentials, private keys, tokens, exploit details, or sensitive user data in a public GitHub issue.

Preferred reporting path:

1. Use GitHub private vulnerability reporting for this repository if it is enabled.
2. Otherwise contact the repository maintainer through a private channel and provide only the minimum details necessary to establish a secure follow-up path.

Public issues are appropriate for non-sensitive hardening suggestions after secrets/exploit material has been removed.

## Secret-handling policy

Never commit or log:

- Supabase service-role keys,
- GitHub access tokens,
- AI provider API keys,
- private keys/certificates,
- service-account credential JSON,
- Sentry auth tokens,
- `PLAN_SIGNING_SECRET`,
- `SECRET_ENCRYPTION_KEY`,
- session/access tokens.

Anything prefixed `VITE_` is browser-visible. A secret must never be moved into a `VITE_*` value to solve a deployment/configuration problem.

## AI BYOK credentials

New user-supplied AI provider credentials are stored through Supabase Vault.

Security requirements:

- browser/authenticated clients never receive decrypted provider keys,
- ordinary `anon`/`authenticated` roles cannot invoke Vault store/read/delete RPCs,
- trusted backend service-role code performs Vault operations,
- application responses expose only safe provider/model/configured metadata,
- provider keys must be redacted from logs and error messages.

The historical `custom_ai_key` field is compatibility-only and should not become the destination for new plaintext credentials.

## GitHub credentials

Stored GitHub credentials use server-side secret sealing.

The secret encryption key is backend-only. If a host/key migration makes an existing sealed envelope unreadable, the application should treat that credential as unavailable and ask for reconnection rather than crashing unrelated authenticated features or exposing ciphertext/plaintext.

## Supabase service role

`SUPABASE_SERVICE_ROLE_KEY` is backend-only and bypasses normal RLS assumptions. It must be available only to the trusted persistent API/runtime that needs it.

Any new service-role operation must be narrowly scoped and reviewed for accidental cross-user access.

## RLS and authorization

User-owned tables must use Row Level Security unless there is a documented server-only reason not to.

Do not solve application errors by disabling RLS or broadly granting access.

When adding a table/function:

- define ownership model,
- add least-privilege policies,
- explicitly review `anon`, `authenticated`, and `service_role` access,
- verify the resulting permissions after migration.

## Repository write safety

RepoFinisher's repository-write path must retain:

- exact plan hash binding,
- base SHA binding,
- stale-base rejection,
- safe path/content validation,
- protected-file rules,
- isolated branch creation,
- draft PR boundary,
- verification before success,
- no-auto-merge default.

Do not bypass these controls because an AI agent is "confident."

## Self-healing safety

Self-healing must fix the implementation, not the acceptance criteria.

Automatic repair must not weaken/delete/skip tests, remove checks, alter security governance, expose secrets, or repeat an identical known-failed patch.

Low-confidence repairs should stop and surface the blocker.

## SSRF and network access

Any server-side URL probe or deployment verification must defend against SSRF.

At minimum:

- restrict schemes,
- reject embedded credentials/unexpected ports,
- prevent private/loopback/link-local targets,
- control redirects,
- prefer allowlisted hosted-preview providers where possible,
- bound request time and response handling.

## CORS

Production authenticated API access must use explicit first-party origins. Do not replace the production CORS policy with a wildcard to work around a frontend migration.

## Dependency and workflow security

CI/workflows generated by RepoFinisher must not introduce privileged constructs such as broad write-all permissions or secret-exposing trigger patterns without explicit manual review.

Dependency upgrades should be reviewed for runtime/security impact, not accepted solely because an automated tool proposed them.

## Database migrations

Migrations are production code.

Security review should consider:

- destructive operations,
- RLS/policy changes,
- grants/revokes,
- `security definer` functions,
- search paths,
- data transformations,
- secret migration behavior,
- service-role-only functions.

## Logging and observability

Logs/traces/events must not include secret values.

CI failure evidence and external logs should be redacted before being sent to an LLM where feasible.

Safe metadata includes provider name, model name, configured/not-configured state, status code, redacted error class, and opaque secret identifiers when necessary.

## Hosting policy

Vercel is not an approved deployment target for RepoFinisher. Security/deployment fixes must use Netlify, Render, Supabase, and GitHub according to the architecture docs.

Do not add an unreviewed hosting provider or new third-party secret store simply to bypass an outage.

## Security changes and CI

Security-sensitive changes should be isolated in focused PRs when practical and must not be merged around failing tests/typechecks/builds.

Update this file and `AGENTS.md` when the security model materially changes.
